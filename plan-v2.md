# plan-v2.md — что добавить в помощь куратору (план от 04.10.2026)

> Статус: **черновик для обсуждения**. Продолжает `futures.md` (оно остаётся историей решений). Работаем **только
> локально**: без push, без деплоя, без коммитов без команды. Данные — только синтетические.

## 0. Где мы сейчас (по коду и CHANGELOG)

| Блок | Что уже работает |
| --- | --- |

| Индивидуальная работа | виды записей, дата события, «вернуться к вопросу», обзор по группе, «нужна работа» (5а) |
| Платформа | колокольчик, роли ×8, CI (pytest на SQLite и MySQL, vitest, build, oxlint, audit), release-сборка |

**Главное наблюдение:** данных уже достаточно, а *времени куратора* платформа пока почти не экономит. Куратор
по-прежнему сам пишет характеристики, отчёты и сообщения родителям и сам ищет, «кому звонить сегодня». Весь план
ниже — про превращение накопленных данных в **готовые действия и документы**.

## 1. Принципы отбора

1. **Экономит время куратора** — приоритет у того, что заменяет ручной Word/Excel.
2. **Использует уже собранное** — без новых форм ввода, где данные уже есть.
3. **Не расширяет круг, видящий особые данные** (152-ФЗ): документы и сводки берут особые поля только если у
   пользователя есть право на них.
4. **Без внешних каналов** (решение 30.09): колокольчик + «скопировать текст» вместо отправки в мессенджеры.
5. Каждый этап — миграция, тесты роль × действие, Vitest, проверка на 375 px.

## 2. Этапы

### Этап 6 — «Мой день» и быстрые действия *(сделано 04.10.2026)*

> Итог: страница, быстрая запись, «позвонить», «сообщение родителям». Отклонение от плана: блок «основания пропусков, которые
> нужно закрыть» не делали — в данных нет статуса «справка не принесена» (только «не требуется»/«подтверждено»). Детали —
> `futures.md`, «Ход этапа 6», `CHANGELOG.md`. Ниже — исходная постановка.

Стартовая страница куратора вместо пустого кабинета. Только агрегация существующих сервисов — новых таблиц нет.

| Блок | Источник данных |
| --- | --- |
| Не сдан день / не отмечены группы | `attendance_service`, календарь |
| Задачи: срок сегодня/просрочено, «возвращено на доработку», ждёт предыдущий шаг | `task_service` |
| Нужна индивидуальная работа (серия пропусков, 14 дней без записей) + «вернуться к вопросу» сегодня | `individual_work_service` |
| **Дни рождения** на неделю (с отметкой, у кого сегодня) | `student_profiles.birth_date` |
| Основания пропусков, которые нужно закрыть (справка не принесена) | `attendance_marks.basis_status` |
| Для зав. отделением: очередь проверки, группы без куратора/без сданного дня | уже есть, свести на одну страницу |

Быстрые действия в карточке студента и журнале (особенно на телефоне): **позвонить** представителю (`tel:`),
**«Скопировать сообщение родителям о пропусках»** (готовый текст по шаблону с датами, без отправки),
**«Быстрая запись»** (заметка в индивидуальную работу одной формой прямо из строки журнала).

Тесты: роль × видимость блоков; число SQL-запросов не растёт с числом групп (как в соц. паспорте).

### Этап 7 — Документы по шаблону (5б) *(≈ 2 недели)*

Самая ощутимая экономия: характеристика, представление, ходатайство, справка-вызов, список группы, акт обследования
жилищно-бытовых условий.

- Формат — **.docx** (`python-docx` или `docxtpl`; в `requirements.in` + пересборка lock, CI это проверяет).
- Шаблон = файл с метками `{{student.full_name}}`, `{{group.name}}`, `{{curator.full_name}}`, `{{attendance.percent}}`,
  `{{guardians}}`… Набор меток фиксирован и документирован (раздел в README).
- Встроенные шаблоны + администратор/воспитательный отдел **загружает свои** (образцы колледжа — ❓ вопрос 11 из
  `futures.md`). Хранение шаблонов — на локальном диске (небольшие файлы); проверка типа по содержимому, лимит размера
  и защита от zip-бомб (уже есть `core/xlsx.check_zip_safety` — обобщить).
- Режимы: один студент / вся группа (zip). Перед скачиванием — **предпросмотр текста с правкой** (куратор
  дописывает вручную, платформа ничего не придумывает).
- **Право на метки**: особые поля (ОВЗ, учёт ПДН/КДН, соц. статус) подставляются только ролям с правом, и каждая
  генерация пишется в журнал (кто, какой студент, был ли особый блок).
- Документы **не хранятся** на сервере (генерация «на лету»), в базе — только запись о факте генерации.

### Этап 8 — «Отчёт куратора» за месяц/семестр *(≈ 1–1,5 недели)*

Куратор регулярно пишет отчёт о воспитательной работе. Платформа собирает **черновик** из того, что уже есть:
посещаемость и дисциплина группы, число бесед/вызовов/Советов профилактики (индивидуальная работа), выполненные
задачи и их статусы, «Доп. образование» (кружки), дни рождения/события. Выход — docx по шаблону этапа 7 и Excel.
Зав. отделением — сводный отчёт по своим группам. Это закрывает идею «отчёты по плану воспитательной работы» без
отдельного ввода данных.

### Этап 9 — План воспитательной работы и мероприятия *(≈ 2 недели)*

- Таблицы `events` (группа/отделение/колледж, дата, тип: классный час, собрание, экскурсия, конкурс, волонтёрство;
  тема, ответственный, итог) и `event_participants` (студент, роль/результат).
- Кураторский **план на семестр** (из шаблона администрации, как шаблоны задач) → факт → «выполнено/перенесено».
- Участие в мероприятии автоматически даёт запись в «Доп. образование/активность» (связь с этапом 4а) и в портфолио.
- Мероприятия колледжа от администрации (как задача, но без формы ответа): «явка группы» одной отметкой.
- Календарь группы: учебные дни + события + сроки задач на одной ленте.

### Этап 10 — Родительские собрания и работа с семьёй *(≈ 1 неделя)*

- Протокол собрания: дата, повестка, явка родителей (по представителям из досье), решения, «поручения» с датами
  (интегрируются в «Вернуться к вопросу»), вывод в docx (этап 7).
- Журнал контактов с родителями: из индивидуальной работы (вызов, звонок) — сводка «когда последний раз связывались»
  по каждому студенту; подсветка «давно не было контакта» для группы риска.

### Этап 11 — Группа риска (объяснимые правила, не ML) *(≈ 1 неделя)*

Композитный индикатор по студенту **с объяснением «почему»**: серия неуважительных пропусков, рост доли пропусков
за 30 дней к предыдущим 30, отсутствие записей индивидуальной работы, просроченный «вернуться к вопросу», открытые
основания пропусков, наличие Совета профилактики. Пороги — в настройках. Особые данные в расчёт **не входят**
(иначе индикатор раскроет их тем, кто их не видит). Выход: список «внимание» на «Мой день» и в обзоре индивидуальной
работы; в паспорте группы — число студентов в зоне внимания.

### Этап 12 — Объявления, начало учебного года, портфолио *(≈ 3 недели, перед сентябрём 2027)*

- **Объявления** администрации с отметкой «прочитано» (на базе колокольчика; охват как у задач).
- **Начало года одной операцией**: перевод групп на следующий курс, выпуск, приём новых групп, закрытие
  периодов; обязательный предпросмотр и откат (самая рискованная операция — делаем с резервной копией и тестом на
  данных размером с реальную базу). Закрывает TODO «перевод студента в другую группу переносит всю историю» —
  нужна история состава групп.
- **Портфолио/рейтинг активности** студента и группы из событий и «Доп. образования»; выгрузка.
- **Срок хранения и автообезличивание** выпускников/отчисленных (❓ вопрос 4 — решение колледжа): служебная
  процедура при открытии платформы + журнал.

## 3. Что **не** рекомендую (пока)

- Расписание и замены — отдельный большой продукт и источник данных извне; без интеграции (❓ из какой системы)
  будет ручным и быстро устареет.
- Telegram/e-mail/SMS-рассылки из платформы — решение 30.09, да и это новые каналы с ПДн; «скопировать текст» закрывает 90 %.
- Портал студента/родителя — расширяет круг субъектов и поверхность атаки; после стабилизации и согласий.
- ML-скоринг рисков — объяснимые правила дают тот же результат и проходят проверку по 152-ФЗ.

## 5. Организация разработки (Claude Code)

Добавлено в проект (локально, `.claude/` в `.gitignore`; `.mcp.json` и `CLAUDE.md` лежат в корне):

| Что | Файл | Зачем |
| --- | --- | --- |
| Память проекта | `CLAUDE.md` | правила «только локально», роли, команды, грабли — не объяснять каждый раз |
| Хук-защита | `.claude/hooks/guard.py` | запрет `git push`, правок `.env`/lock-файлов/`release/`, чтения реальных ПДн |
| Хук-проверка | `.claude/hooks/post_edit.py` | `oxlint` на изменённый `.ts(x)` и `py_compile` на `.py` сразу после правки |
| Права | `.claude/settings.json` | тесты/сборка/линтер без запросов, `git push` в deny |
| Скиллы | `check-all`, `new-migration`, `new-endpoint`, `finish-stage`, `ui-check` | типовые операции этапа |
| Субагенты | `access-reviewer`, `ui-reviewer` | ревью прав/ПДн и мобильного интерфейса |
| MCP | `context7` | актуальные доки FastAPI/SQLAlchemy 2/React 19/Vite 8/Vitest 5 (версии новее знаний модели) |

Рабочий цикл этапа: план → `/new-migration` → код → `/new-endpoint` (чек-лист) → тесты → `access-reviewer` +
`ui-reviewer` → `/ui-check` → `/check-all` → `/finish-stage`.
