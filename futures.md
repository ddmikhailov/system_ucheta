# futures.md — от учёта посещаемости к платформе-помощнику куратора

> Статус: **черновик для обсуждения**. Работаем **только локально**: ничего не пушим в GitHub, не деплоим на Amvera,
> не коммитим без явной команды. Вопросы, на которые нужен ответ, собраны в разделе 9 и помечены `❓`.

## 0. Цель

Сейчас платформа умеет одно: отмечать посещаемость и строить по ней витрины. Цель — сделать из неё рабочее место
куратора, где есть:

1. **Досье студента** — вся информация о студенте в одной карточке: персональные данные, семья, здоровье/льготы
   (если разрешено), учёба, посещаемость, доп. образование, заметки куратора, документы.
2. **Задачи от администрации** — администрация ставит задачу («собрать кружки по каждому студенту», «снять
   видеовизитку группы»), куратор её выполняет в платформе, зав. отделением проверяет, администрация видит сводку.
3. **Напоминания** о сроках задач и о посещаемости: в интерфейсе (колокольчик) и в Telegram.

Посещаемость остаётся ядром и не ломается.

## 1. Досье студента

### 1.1 Что видит куратор
Карточка студента открывается по клику на ФИО в журнале, в списке группы и в витринах. Вкладки:

| Вкладка | Содержимое |
| --- | --- |
| Основное | ФИО, фото, дата рождения, группа, курс, форма обучения (бюджет/договор), статус, даты зачисления/выбытия, телефон, e-mail, соцсети/мессенджер |
| Семья и контакты | законные представители (ФИО, кем приходится, телефон), адрес регистрации и проживания, общежитие (корпус/комната) |
| Социальный статус | сирота/под опекой, инвалидность/ОВЗ, многодетная/малоимущая семья, учёт (ПДН/КДН, внутренний), стипендия/соцвыплаты |
| Учёба и посещаемость | процент за период, серия пропусков, история отметок, периоды отсутствия (данные уже есть) |
| Доп. образование и активность | кружки, секции, волонтёрство, конкурсы, достижения — наполняется в том числе **автоматически из задач** (см. 2.6) |
| Заметки куратора | лента записей: беседы, звонки родителям, инциденты, договорённости, с датой и автором |
| Документы | справки, заявления, приказы, скан-копии (файлы) |
| История | кто и когда менял данные карточки (журнал изменений) |

### 1.2 Как устроено технически
- **Фиксированные поля** (то, что есть у всех и по чему нужны фильтры/отчёты) — обычные колонки в таблицах
  `students`, `student_contacts` (представители), `student_social` и т.п.
- **Настраиваемые поля** — администратор сам добавляет поле в карточку («Размер одежды», «Прививка от гриппа»),
  не дожидаясь программиста. Хранение: справочник `student_field_definitions` (название, тип, раздел, кто видит,
  кто правит) + значения `student_field_values` (или JSON-колонка). Типы: текст, число, дата, да/нет, выбор из
  списка, множественный выбор, файл.
- **Заметки** — таблица `student_notes` (автор, дата, текст, тип, видимость).
- **Документы** — таблица `student_documents` + файловое хранилище (раздел 5).
- **Журнал изменений** — каждая правка поля пишет старое/новое значение в `audit_log` (уже есть механизм).

### 1.3 Как данные попадают в досье
1. Массовый импорт из Excel (шаблон выгружаем из платформы: колонки = поля карточки) — для старта года.
2. Ручное заполнение куратором в карточке.
3. Автоматически из результатов задач (кружки → «Доп. образование»).
4. (Опционально) анкета, которую заполняет сам студент/родитель по ссылке — ❓ нужна ли.

### 1.4 Доступ и 152-ФЗ — самое важное
Досье резко увеличивает объём и чувствительность ПДн (здоровье, соц. статус, учёт — это **специальные категории**).
- Куратор видит только студентов своих групп (как сейчас с посещаемостью); заместитель — только на время замещения.
- Поля размечены уровнем чувствительности: `обычные` / `контакты` / `особые` (здоровье, инвалидность, учёт в ПДН).
  Для каждого уровня — кто видит (куратор, зав. отделением, воспитательный отдел, соц. педагог, психолог, админ).
- **Журнал просмотров** особых полей и документов (кто открыл карточку/файл и когда).
- Шифрование особых полей в БД и файлов на диске; ограничение выгрузок особых полей.
- Удаление/обезличивание досье при отчислении через N лет (срок хранения — решение колледжа).
- Нужны: согласие на обработку ПДн, приказ о допуске сотрудников, модель угроз — это организационная часть.

## 2. Задачи от администрации

### 2.1 Понятия
- **Задача** — то, что создаёт администрация: название, описание, срок, кто ставит, кто проверяет.
- **Охват** — на кого задача распространяется: весь колледж / отделения / курсы / конкретные группы (с исключениями).
- **Режим сбора**:
  - `по группе` — один ответ от группы (видеовизитка, план воспитательной работы, фото мероприятия);
  - `по каждому студенту` — строка на каждого студента (кружки, флюорография, согласия);
  - `по выбранным студентам` — куратор сам отмечает, кого касается (только совершеннолетние, только общежитие,
    только участники конкурса), или администрация задаёт фильтр (курс, статус, поле досье).
- **Форма ответа** — набор полей, которые задаёт администратор при создании задачи (конструктор форм):
  да/нет (чекбокс «сдал»), текст, число, дата, выбор, множественный выбор (из справочника кружков), файл (видео,
  фото, документ), ссылка, комментарий.
- **Назначение** (assignment) — экземпляр задачи для конкретной группы: у каждой группы свой статус, свои ответы,
  своя история проверки. Исполнитель — ответственный за группу (куратор; при замещении — заместитель).
- **Подзадачи / этапы** — задача может состоять из шагов («1. Сценарий видеовизитки до 10.10 → 2. Видео до 20.10»),
  каждый шаг со своим сроком, формой и проверкой; следующий открывается после сдачи или приёмки предыдущего.

### 2.2 Жизненный цикл назначения
```
Не начато → В работе (черновик сохраняется) → Отправлено на проверку → Принято
                                                     ↘ Возвращено на доработку (с комментарием) → В работе
Просрочено — признак поверх любого статуса, если срок прошёл, а «Принято» нет.
```
Проверяющий по умолчанию — зав. отделением группы; настраивается в задаче (воспитательный отдел, конкретный
сотрудник, «без проверки — сразу принято»). Комментарии можно оставлять и к назначению целиком, и к строке
конкретного студента («у Иванова не указан кружок»).

### 2.3 Экраны
- **Администрация → «Задачи»**: список задач с прогрессом (сдано 30/44, принято 25, просрочено 4); создание задачи
  (мастер: описание → охват → режим сбора → форма → срок и проверка → напоминания); матрица «группа × статус»;
  сводная таблица ответов с фильтрами; выгрузка в Excel (по каждому студенту — строка); массовое напоминание.
- **Куратор → «Мои задачи»**: карточки задач с дедлайнами и статусом; внутри — таблица студентов с полями формы
  (как журнал посещаемости: быстро пройтись по списку), автосохранение черновика, кнопка «Отправить на проверку»,
  переписка с проверяющим.
- **Зав. отделением → «На проверке»**: очередь назначений своего отделения, просмотр ответов/видео, «Принять» /
  «Вернуть с комментарием».

### 2.4 Как ложатся ваши примеры
| Пример | Настройка задачи |
| --- | --- |
| Кружки доп. образования | охват: все группы; режим: по каждому студенту; форма: «Кружки» (множественный выбор из справочника кружков + «Другое» текстом), «Не посещает» (да/нет); проверка: зав. отделением; результат пишется в досье |
| Видеовизитка группы | охват: все группы; режим: по группе; форма: «Видео» (файл или ссылка на VK Видео/Я.Диск), «Сдано» (чекбокс); оценка: поле «Баллы/оценка» у проверяющего; напоминания за 3 дня и в день срока |

### 2.5 Технически (модель данных)
```
tasks                (id, title, description, created_by, reviewer_rule, collect_mode, due_at, status, parent_task_id)
task_scope           (task_id, department_id | course | study_group_id, include/exclude)
task_fields          (task_id, key, label, type, required, options_json, writes_to_student_field)
task_assignments     (id, task_id, study_group_id, assignee_user_id, status, submitted_at, reviewed_by, reviewed_at, score)
task_rows            (assignment_id, student_id NULL для «по группе», values_json, is_included)
task_comments        (assignment_id, student_id NULL, author_id, text, created_at)
task_files           (row_id, file_id)          -- ссылки на файловое хранилище
```
Ответы — в JSON по схеме полей задачи (разные задачи = разные формы, без миграций БД на каждую задачу).
При создании задачи назначения генерируются по охвату; при появлении новой группы/студента после старта —
правило: добавлять или нет (❓).

### 2.6 Связь задач с досье
Поле формы можно связать с полем досье («Кружки» → «Доп. образование»). После приёмки значения записываются в
карточку студента с пометкой «из задачи №…». Так задачи постепенно наполняют досье, и следующий раз ту же
информацию не нужно собирать с нуля (форма откроется уже заполненной — куратор только проверяет изменения).

### 2.7 Шаблоны и повторяющиеся задачи
- Сохранить задачу как шаблон и запускать заново («Отчёт о воспитательной работе за месяц»).
- Периодические задачи: каждый месяц/семестр автоматически.

## 4. Что ещё можно добавить (предложения, обсудить приоритет)
1. **Социальный паспорт группы** — автоматическая сводка из досье (сколько сирот, ОВЗ, многодетных, в общежитии),

2. **План воспитательной работы и журнал мероприятий** — классные часы, собрания, мероприятия с датой, темой,

3. **Журнал индивидуальной работы** со студентом группы риска (беседы, приглашение родителей, Совет профилактики)

4. **Родительские собрания** — протокол, явка родителей, решения.
5. **Генерация документов по шаблону** — характеристика, представление, ходатайство, списки группы (docx/PDF из
   данных досье).
6. **Дни рождения** группы в кабинете куратора.
7. **Контакты для экстренной связи** одной кнопкой (позвонить родителю из карточки на телефоне).
8. **Портфолио/рейтинг активности** студента и группы (конкурсы, волонтёрство).
9. **Объявления** от администрации всем кураторам (без сбора ответа, с отметкой «прочитано»).
10. **Роли соц. педагог и психолог** с доступом к особым полям досье.
11. **Начало учебного года** — перевод групп на следующий курс, выпуск, приём новых групп одной операцией.

## 5. Файлы (видео, документы, сканы)
- Видеовизитки весят сотни мегабайт — нужны загрузка по частям (resumable), лимиты размера и типов, прогресс.
- Где хранить: локально — папка на диске/Docker-volume; в проде — S3-совместимое хранилище (Yandex Object Storage,
  VK Cloud, Selectel) с приватными ссылками на ограниченное время. ❓ Альтернатива: не хранить видео у себя, а
  принимать ссылку на VK Видео / Яндекс Диск / RUTUBE.
- Проверка типа файла по содержимому, антивирус (ClamAV) — опционально.
- Доступ к файлу — через проверку прав (как к карточке), журнал скачиваний для документов с ПДн.

## 6. Изменения в архитектуре
- **Backend:** новые модули `students_profile`, `tasks`, `files`, `notifications` (расширение); сервис политик
  (`app/core/policies.py`) дополняется правами на досье и задачи; фоновые задания планировщика для напоминаний.
- **Frontend:** новые разделы «Студенты» (карточка), «Задачи» (куратор/проверяющий/администрация), конструктор
  форм; единый компонент «таблица студентов с полями» для журнала посещаемости и задач.
- **БД:** миграции Alembic на каждый этап; JSON-колонки (MySQL 8 поддерживает).
- **Локальная разработка:** docker compose (app + MySQL + при необходимости MinIO как локальный S3), seed с
  синтетическими студентами и примерами задач. Реальные ФИО и ПДн в разработке не используем.
- **Тесты:** на каждую роль × действие (как `test_policies_matrix.py`), особенно доступ к досье.

## 8. Риски
- ПДн особых категорий: утечка = серьёзные последствия (152-ФЗ, штрафы). Без организационных мер (согласия, приказ,
  ответственный) досье с особыми полями запускать нельзя.
- Конструктор форм легко переусложнить — начинаем с 8–10 типов полей.
- Видео: объём хранилища и трафик; решение «ссылка вместо файла» снимает проблему.
- Нагрузка на кураторов: всё, что можно заполнить автоматически (из досье, из прошлых задач), должно заполняться.

## 9. Принятые решения (допрос 30.09.2026)

| Вопрос | Решение | Что это меняет в плане |
| --- | --- | --- |
| Состав досье | Все 4 блока: основное и контакты, родители/представители, соц. статус и льготы, **здоровье и учёт (ОВЗ, ПДН/КДН)** | Особые категории ПДн есть → обязательны уровни доступа, журнал просмотров, шифрование полей (1.4) |
| Кто видит особые данные | Куратор (своих), зав. отделением (своё отделение), воспитательный отдел, админ/тьютор, **новые роли соц. педагог и психолог** | Добавляем 2 роли; соц. педагог и психолог видят досье, но не управляют структурой и посещаемостью |
| Источник данных | **Импорт из Excel** администрацией + ручное дополнение куратором | Этап 1 начинается с шаблона Excel и импорта с предпросмотром ошибок; анкета по ссылке и интеграция с 1С — не сейчас |
| Файлы / видеовизитки | **Сдаются ссылкой** (VK Видео, Я.Диск, RUTUBE) | Раздел 5 упрощается: хранилище для видео не нужно; файлы только для документов досье (сканы справок) — небольшие, на локальный диск |
| Кто создаёт задачи | Админ/тьютор и воспитательный отдел — по колледжу; **зав. отделением — для своего отделения**. Куратор задачи не создаёт | Охват задачи зав. отделением ограничен его отделением (как с витринами) |
| Проверка | **Настраивается в задаче**: по умолчанию зав. отделением; можно «автор задачи», две ступени или без проверки | `reviewer_rule` в задаче + цепочка шагов проверки |
| Оценка | **Только «принято / возвращено»**, без баллов | Поле score не делаем |
| Новый студент после старта задачи | **Добавляется, пока назначение не отправлено на проверку** | При изменении состава группы — пересчёт строк открытых назначений |
| Каналы напоминаний | **Только колокольчик** в платформе | Telegram/e-mail не трогаем; напоминания — задания планировщика, пишущие in-app уведомления |
