# КАИТ-20 — платформа учёта посещаемости

Реализация концепции (`Концепция платформы учёта посещаемости.md`), этапы
0–2: справочники, ядро (вход и роли, личный кабинет куратора, экран
отметки, «Сдать день», витрины, экспорт в Excel/PDF, админ-панель) и
Telegram-бот с планировщиком напоминаний.

## Стек

- Backend: Python 3.14, FastAPI, SQLAlchemy 2, Alembic, PyMySQL
- БД: MySQL 8.4 LTS, InnoDB, utf8mb4
- Бот: aiogram 3, планировщик: APScheduler — оба встроены в тот же процесс
- Frontend: React + TypeScript, Vite — собирается в статику, её отдаёт backend
- Упаковка: Docker Compose, 2 контейнера (`app` + `db`)

## Архитектура: почему единое приложение

Backend, Telegram-бот, планировщик и отдача фронтенда — один процесс, один
Docker-образ, один контейнер (`app`). Отдельно снаружи остаётся только
MySQL — это внешняя стейтфул-зависимость (свой том, свои бэкапы), а не
часть платформы.

Так было не всегда: изначально бот и планировщик были отдельными
процессами (собственный `Bot`/`Dispatcher` у бота, свой `AsyncIOScheduler`
у планировщика), а фронтенд отдавался отдельным nginx-контейнером — итого
5 сервисов. Технической необходимости в этом не было: FastAPI/uvicorn,
aiogram и APScheduler — все три построены на asyncio, поэтому бот и
планировщик запускаются как фоновые задачи в `lifespan` FastAPI
(`app/main.py`, логика — в `app/worker_runtime.py`), а собранный
`frontend/dist` backend отдаёт напрямую через `StaticFiles` + SPA-фоллбэк.
Пять контейнеров для проекта такого масштаба (44 куратора, один колледж)
были бы той же ошибкой, от которой концепция сознательно отказалась,
выбрав APScheduler вместо Celery/Redis — микросервисная декомпозиция ради
самой декомпозиции.

Раздельный режим (`bot/main.py`, `scheduler/main.py` как самостоятельные
процессы) в коде сохранён на случай, если проект вырастет настолько, что
рассылки понадобится вынести на отдельный ресурс — переключается флагом
`EMBED_WORKERS=false`. Логика бота и планировщика не продублирована: и
встроенный, и раздельный режимы вызывают одни и те же функции из
`app/worker_runtime.py`.

## Структура

```
Dockerfile         Единая сборка: сначала фронтенд (node), потом backend (python) + его статика
backend/
  app/        FastAPI-приложение, модели, миграции, сервисы, worker_runtime.py
  bot/        Обработчики бота (aiogram) — /start и кнопки в напоминаниях
  scheduler/  Задания планировщика (APScheduler)
  scripts/    seed.py, import_source_data.py
  tests/      pytest-набор
frontend/   React-приложение (личный кабинет, витрины, админ-панель)
docker-compose.yml   2 сервиса: app + db
```

## Запуск через Docker Compose

```bash
cp backend/.env.example backend/.env
# отредактируйте backend/.env — обязательно задайте DB_PASSWORD, DB_ROOT_PASSWORD,
# JWT_SECRET (случайная строка ≥32 символов, иначе приложение откажется стартовать
# — python -c "import secrets; print(secrets.token_urlsafe(32))"), ADMIN_PASSWORD,
# и, если нужен бот, TELEGRAM_BOT_TOKEN/TELEGRAM_BOT_USERNAME/WEB_APP_BASE_URL

docker compose up -d --build
```

Миграции, справочники и вход администратора контейнер накатывает сам при
старте (`backend/docker-entrypoint.sh`) — дополнительно ничего выполнять не
нужно. Импорт CSV-выгрузок — отдельно, см. «Импорт данных» ниже.

После этого веб-интерфейс и API — на одном адресе, http://localhost:8000.
Swagger (`/docs`, `/openapi.json`) в этом режиме выключен по умолчанию
(`ENVIRONMENT=production`) — включите `ENVIRONMENT=development` в `.env` для
локальной разработки. Логин администратора — `ADMIN_USERNAME`/`ADMIN_PASSWORD`
из `.env`; если пароль не задан явно, он генерируется случайно и **не**
печатается в лог — заданный пароль (или сгенерированный при первом старте,
который тогда нужно посмотреть в БД/пересоздать явным `ADMIN_PASSWORD`)
всё равно потребуется сменить при первом входе.

## Импорт данных «Диджитал»

`backend/scripts/import/data/{groups,curators,students}.csv` — реальные ФИО
студентов и кураторов колледжа, поэтому файлов нет в публичном репозитории
(`.gitignore`) — их кладут на сервер отдельно, вне git. При подготовке
исходных выгрузок устраняются типовые дефекты Яндекс.Таблиц (неразрывные
пробелы в ФИО, задвоенные списки группы и т.п.) — см.
`backend/scripts/import/data/README.md` на самом сервере. Отметки
посещаемости за прошлые периоды не переносятся — `attendance_marks`
стартует пустой.

`scripts.import_source_data` идемпотентен — повторный запуск не создаёт
дублей существующих групп/студентов/кураторов, но не идеален по данным,
которые уже изменили руками после импорта (переименование, удаление) —
поэтому это разовая ручная операция, а не то, что должно выполняться на
каждом старте контейнера. Включается переменной окружения
`IMPORT_ON_START=true` только на тот один деплой, где выгрузка реально
нужна (`docker-entrypoint.sh` запускает импорт лишь при этом флаге), и
сразу выключается обратно — по умолчанию (`false`) импорт пропускается.
Группы без куратора остаются без назначения — по концепции такие группы
должны вестись зав. отделением, пока куратор не назначен через раздел
«Группы» админ-панели (кнопка «Назначить куратора») или
`POST /admin/curator-assignments`.

После импорта выдайте кураторам временные пароли — раздел «Пользователи»
админ-панели, профиль пользователя → «Выдать пароль» (или
`POST /admin/users/{user_id}/set-password`). При первом входе система
обязывает задать собственный пароль.

## Локальная разработка без Docker

Backend:

```bash
cd backend
pip install -r requirements-dev.txt
cp .env.example .env   # укажите доступ к локальному MySQL
alembic upgrade head
python -m scripts.seed
python -m scripts.import_source_data
uvicorn app.main:app --reload
```

Frontend:

```bash
cd frontend
npm install
npm run dev
```

## Автотесты

```bash
cd backend
pip install -r requirements-dev.txt

```

176 тестов (включая асинхронные — нужен `pytest-asyncio`, тоже в
`requirements-dev.txt`), каждый — на изолированной SQLite-БД (создаётся
заново во временном файле на каждый тест, `tests/conftest.py`), реальному
MySQL, `.env` или токену бота не нужны. Набор для импорта — синтетический
(`tests/fixtures/import/*.csv`): та же форма, что у реальной выгрузки
«Диджитал» (44 группы/989 студентов/24 куратора/3 вакансии, коды и курсы
групп совпадают), но с полностью выдуманными ФИО — реальные ФИО студентов
и кураторов в репозиторий не попадают (`backend/scripts/import/data/*.csv`
с настоящими данными — не в git, только на сервере). Покрытие:

- `test_seed_and_import.py` — идемпотентность справочников и импорта, точные

обнаруженные именно тестами на permissions: `/dashboards/*` и
`/export/excel` были доступны любому авторизованному пользователю без
проверки роли (см. историю изменений `app/api/deps.py`, `dashboards.py`,
`export.py`).

## Админ-панель

Доступна по `/admin`. Разграничение внутри панели соответствует ролям из
концепции:

- **Администратор** (и тьютор — те же права по всему колледжу) — единственные,
  кто создаёт отделения, группы, студентов и пользователей, выдаёт пароли.
- **Воспитательный отдел** (и администратор) — правит справочник кодов
  отметок (флаги `counts_as_present`/`is_excused`/`requires_document`) и
  учебный календарь (исключения из умолчания «будни — учебные»).
- **Зав. отделением** до полной админ-панели не допускается (в интерфейсе
  нет пункта навигации, backend отдаёт 403 на структурные операции) — по
  концепции его правки ограничены своим отделением. Закрывать вакантные
  группы своего отделения он может через отдельный экран в витринах (см.
  «Вакантные группы» ниже), не заходя в саму админ-панель.

Приглашений по почте/ссылке нет (см. историю — были в ранней версии и убраны):
администратор/зав. отделением создаёт учётную запись и сразу выдаёт временный
пароль (кнопка «Копировать»), при первом входе система обязывает сменить его
на свой.

## Вакантные группы

Вкладка «Вакантные группы» в витринах — реализация правила концепции
«группа никогда не остаётся без ответственного». Зав. отделением видит
только вакансии своего отделения и назначает куратора или заместителя тем
же диалогом, что и в админ-панели (общий компонент `AssignCuratorModal`),
не заходя в саму панель.

Это потребовало закрыть реальный пробел в скоупинге, вскрывшийся при
проектировании экрана: `GET /admin/groups`, `GET /admin/students`, `GET
/admin/users` не ограничивали зав. отделением его собственным отделением
— он мог запросить список групп/студентов/пользователей любого другого
отделения (передав `department_id` или вовсе без фильтра), а `POST
/admin/curator-assignments` позволял назначить куратора на чужую группу
или назначить куратора не из своего отделения. Теперь для роли
`dept_head` все четыре эндпоинта принудительно ограничены его
`department_id` — параметр `department_id` в query не позволяет это
обойти. Роли `edu_department`/`admin` работают как раньше, без
ограничений. Проверено `tests/test_api_dept_head_scoping.py` — с реальным
вторым отделением и его куратором, специально заведёнными в тесте.

## Telegram-бот и планировщик

Реализация раздела концепции «Telegram-бот». Наружу у платформы ровно одно
соединение — бот к Telegram API (лонг-поллинг, входящих портов не
открывает).

### Настройка

```
TELEGRAM_BOT_TOKEN=<получить у @BotFather>
TELEGRAM_BOT_USERNAME=<имя бота без @>
NOTIFICATION_TIMEZONE=Europe/Moscow
WEB_APP_BASE_URL=https://<домен веб-интерфейса>
```

Пустой `TELEGRAM_BOT_TOKEN` полностью отключает бота и планировщик — веб-
платформа при этом работает как обычно (`settings.telegram_enabled`).

### Подключение аккаунта

Кнопка «Подключить Telegram» есть в шапке у любой роли (не только у
куратора — дайджесты получают и зав. отделением, и воспитательный отдел).
Она вызывает `POST /auth/telegram/link`, создаёт одноразовый токен
(`telegram_link_tokens`, живёт `TELEGRAM_LINK_TOKEN_TTL_MINUTES`, по
умолчанию 10 минут) и отдаёт диплинк `t.me/<бот>?start=<token>`. Бот не
может написать первым, пока пользователь сам не перешёл по ссылке — это
ограничение Telegram, не платформы. Отключение — `POST
/auth/telegram/unlink`, в один клик, номера телефонов нигде не хранятся.

### Расписание рассылок (`app/worker_runtime.py`)

| Время (по умолчанию) | Кому | Что |
| --- | --- | --- |
| 10:00 | Куратору/заместителю с несданными группами | Список групп, кнопки «Все присутствуют» и «Открыть» |
| 15:00 | Тем, кто всё ещё не сдал | Повторное напоминание |
| 15:30 | Зав. отделениями | Несданные группы своего отделения с ФИО ответственного |
| 16:00 | Воспитательному отделу | Сдано N из 44, процент присутствия, проблемные группы |
| Пятница 16:30 | «Руководству» (см. ниже) | Недельный дайджест: динамика, дисциплина сдачи, риск-группа |

Все времена и часовой пояс настраиваются через `.env`. В выходные,
праздники и каникулы (по `academic_calendar`) бот молчит — рассылки не
идут. Каждая отправка проверяет `notification_log` перед отправкой, так
что перезапуск планировщика не задваивает напоминание и лимит «не больше
двух напоминаний в день» соблюдается по построению (ровно два ежедневных
слота, оба — только для ещё не сдавших).

На время замещения (активная запись `curator_assignments` с
`role_type=deputy`, покрывающая дату) напоминания уходят заместителю, а не
основному куратору — это единственный сигнал «куратор в отпуске», который
есть у платформы; отдельного поля «куратор недоступен» не заводили.

«Руководство» — не роль с правами доступа (в концепции такой роли нет), а
просто отметка `receives_leadership_digest` у произвольной учётной записи;
включается в админ-панели, вкладка «Пользователи», галочка «Дайджест
рук-ва» (только администратор).

### Запуск

По умолчанию отдельно ничего не запускается — бот и планировщик стартуют
сами, фоновыми задачами внутри `uvicorn app.main:app` (см. «Архитектура»
выше). `python -m bot.main` / `python -m scheduler.main` нужны, только
если явно выставлен `EMBED_WORKERS=false` и вы разворачиваете их отдельными
процессами/контейнерами.

### Проверено

- Весь пайплайн заданий планировщика проверен pytest'ом с подменным `Bot`
  (`tests/test_scheduler_jobs.py`) — включая замещение куратора
  заместителем, пропуск выходных, отсутствие повторной отправки и то, что
  сдавшая день группа выпадает из напоминания.
- Привязка/отвязка аккаунта, одноразовость токена, конфликт «этот chat уже
  привязан к другому пользователю» — `tests/test_telegram_link_service.py`,
  `tests/test_api_telegram.py`.
- Живой бот (реальный токен от @BotFather): встроенный запуск проверен
  вручную — `uvicorn app.main:app` с заполненным `TELEGRAM_BOT_TOKEN`
  поднимает APScheduler (все 5 заданий) и aiogram-поллинг в одном
  процессе, бот реально подключается к Telegram API, при этом
  `/health` и остальной API продолжают отвечать. Сама доставка сообщений
  по расписанию (реальные напоминания в реальном чате) проверяется уже на
  тестовом стенде, не локально.
- UI подключения (модалка, диплинк, кнопка «Я подключил — проверить») —
  вручную в браузере.

## Дизайн

Визуальное оформление приведено в соответствие с брендбуком КАИТ №20
(единая выжимка правил, `frontend/src/index.css`):

- **Цвет.** Официальный файл логотипа — приоритетный источник (выше таблицы
  цветов брендбука, где приоритет и указан): пипеткой снят фиолетовый
  `#533D8F`. Он же — середина базовой оси бренда «глубокий синий → фиолетовый
  → пурпурный», поэтому оба конца достроены: `#2B2C7C` (ультрамарин из
  фирменной таблицы) и `#7A3D9E`. Статусные цвета (присутствие/опоздание/
  отсутствие) — не произвольные веб-цвета, а фирменная дополнительная
  палитра: сигнальный зелёный `#0F8558`, ярко-оранжевый `#FFA421`, красный
  `#CB3334`.
- **Типографика.** Montserrat, самостоятельно захостен (`frontend/src/fonts.css`,
  `.woff2` в `frontend/public/fonts/`), а не подключён через Google Fonts —
  без стороннего запроса при каждой загрузке страницы. Bold для заголовков,
  обычный текст на Medium/Regular, как предписано брендбуком.
- **Логотип.** Используется официальный файл как есть, без каких-либо
  изменений (`frontend/public/kait20-logo.webp`) — на логине и в шапке
  приложения. Не перекрашен, не растянут, без эффектов; вокруг всегда есть
  свободное поле.
- **«Технологичность» сверх обязательного.** Разделённый экран входа с
  фирменным градиентом, тонкой диагональю и точечной сеткой справа — отсылка
  к «дополнительной графике» брендбука (диагональная геометрия у краёв,
  пиксельные сетки, точки-узлы), но не декор логотипа. Тонкая градиентная
  линия под шапкой на каждой странице. Один доминирующий акцент на группу
  действий: фирменный градиент — только на завершающей кнопке («Сдать
  день», «Сохранить»), остальные — нейтральные, чтобы акцент не терялся.

## Резервное копирование MySQL

Процедура и проверка восстановления не были описаны (см. TODO.md 5) —
здесь минимальный рабочий вариант, не привязанный к конкретному хостингу:

```bash
# Бэкап (логический дамп, переносим между версиями MySQL 8.x без проблем)
docker exec kait20_db mysqldump -u root -p"$DB_ROOT_PASSWORD" \
  --single-transaction --routines --triggers kait20 > backup_$(date +%Y%m%d).sql

# Восстановление на чистую БД
docker exec -i kait20_db mysql -u root -p"$DB_ROOT_PASSWORD" kait20 < backup_20260925.sql
```

`--single-transaction` — снимок без блокировки таблиц на время дампа
(InnoDB). Проверка восстановления — обязательный, а не опциональный шаг:
дамп, который ни разу не накатывали обратно, с равной вероятностью либо
рабочий, либо нет. Хранить бэкапы отдельно от сервера с самой БД (иначе
потеря диска убивает и то, и другое) и делать это ежедневно автоматической
задачей на хостинге — Amvera предоставляет управляемый MySQL с собственными
бэкапами; если используется self-hosted MySQL, `cron` + команда выше решают
задачу без дополнительных сервисов.

## 152-ФЗ: работа с персональными данными

Платформа хранит ФИО студентов и сотрудников — персональные данные в
терминах 152-ФЗ. Что сделано технически:

- ФИО кураторов/студентов не попадают в публичный репозиторий (см.
  «Автотесты» — тесты используют синтетический набор, реальные выгрузки —
  только на сервере, `.gitignore`).
- Пароли — только хэши (argon2), временный пароль при выдаче не логируется
  (см. `scripts/seed.py`, `admin.py: set_password`).
- Аудит-лог (`audit_log`) фиксирует, кто и когда менял пользователей,
  студентов, отметки — но не факты чтения/просмотра карточки студента
  (не журналируется отдельно; см. ограничение ниже).
- Комментарии/основания к отметкам — свободный текст, куда куратор может
  вписать что угодно, включая избыточные ПДн (диагнозы, обстоятельства) —
  технически не ограничено (см. TODO.md 5, «Обезличивание неполное»).

Что осталось организационным, не техническим долгом — платформа не может
сама решить эти вопросы, они требуют политики учреждения:

- Согласия на обработку ПДн студентов/сотрудников — сбор и хранение вне
  платформы (бумажный/иной процесс).
- Срок хранения данных отчисленного студента — сейчас не удаляются и не
  анонимизируются автоматически по истечении какого-либо срока; политика
  хранения (сколько лет после отчисления) должна быть зафиксирована
  учреждением, а не выведена из кода.
- Ответственный за обработку ПДн и разграничение по ролям, кто из
  сотрудников колледжа имеет право просматривать чьи данные, — это уже
  реализовано ролевой моделью (см. «Админ-панель»), но формальное
  назначение ответственного лица — не техническая задача.
